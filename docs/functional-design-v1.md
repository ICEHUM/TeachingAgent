# 教学智能体功能设计 v1

状态：设计方案，业务功能尚未实现。界面草图中的学生、任务状态、测试结果均为示例，不是教学应用数据。

## 1. 定位和范围

申报方向：职业院校赛道，高职层次，主要应用场景选择“实践教学与实训智能体”。办学层次与应用场景分别记录，最终报名字段按官网实际表单填写。

产品暂称“AI 应用开发实训教练”。面向人工智能技术应用专业，帮助学生在真实代码与运行环境中完成项目，并让教师掌握学生遇到的困难、给予了哪些帮助、是否能够独立迁移。

用户已确认的首期场景：已有 Python 基础的学生，开展 AI 应用开发实训。以“构建带来源引用的企业 FAQ 问答服务”为一个完整任务模板。知识材料使用教师自编或获授权的公开示例资料，不预设学校已有企业合作。具体班级、课时与基础水平将在试用前核实；控制流程不绑定某一种具体模型。

拟解决的问题需要在首轮访谈和课堂试用中核实：学生调试时依赖整段答案；同一错误反复出现；教师难以及时照顾不同进度；只看最终代码难以了解学习过程。

## 2. 比赛依据和评分对应

依据《首届教学智能体大赛通知(1).pdf》附件3，第19—21页；访问与材料要求另见第18—19、24—25页。以下功能和验收标准是本项目的设计选择，官方未给二级指标独立分值，不能将功能数量换算为得分。

| 官方一级指标 | 分值 | 本项目落实方式 | 需要留下的证据 |
|---|---:|---|---|
| 职业院校特色 | 20 | 岗位任务书、技能目标、验收规范、工作成果交付；以开发、测试、调试和解释为主要活动 | 课程任务与能力点映射、学生作品、教师确认的职业任务背景 |
| 功能设计与智能化水平 | 25 | 读取实际代码、测试结果与学生解释；判断困难、选择指导层级、运行检查、调整下一步建议 | 输入证据、教学策略、工具动作、执行结果和后续反馈的时间线 |
| 教学融合与应用场景 | 25 | 课前发布、课中分层指导与教师介入、课后复盘及迁移任务；练习与考核模式分开 | 一节课完整使用案例、教师介入记录、任务发布和提交快照 |
| 应用成效与推广价值 | 20 | 同量规前后测、无AI迁移任务、错误复发与教师指导耗时记录；任务模板复用 | 样本量、日期、任务版本、评分来源、真实作品和师生反馈 |
| 材料规范与现场展示 | 10 | 可供评审使用的演示入口、匿名展示、脱敏导出、来源与开源组件说明 | 6—10分钟视频、可用测试账号、研发记录及佐证材料 |

职业院校评分表没有给“界面美观”单列分值。前端需要清晰、稳定、易用，让教学流程及智能指导可见；页面数量不能替代教学效果。

官方要求建设说明书不超过3000字、50M；附件5简介1200字以内、应用成效1800字以内。视频6—10分钟、720P及以上、MP4、不超过1200M。现场汇报不超过10分钟，提问5分钟。原始审核材料与匿名评审材料分别管理，学校审核盖章等材料流程由参赛教师办理，系统导出不能代替审核。附件5“应用安全”证明注明若有则勾选，不设计成强制前置认证。

## 3. 前端信息结构

一个网页产品，两种主要角色。学生端和教师端共享任务、提交和评价记录；后端校验每次访问的角色、班级和资源归属。正式系统的角色来自账号权限，草图的角色切换仅用于说明设计。

| 页面 | 核心内容 | 首版优先级 |
|---|---|---|
| 登录与课程入口 | 学生/教师登录、课程班级、独立演示入口 | 必做 |
| 学生·我的实训 | 待开始/进行中/已提交、教师反馈、继续上次任务 | 必做 |
| 学生·实训工作台 | 任务步骤、文件与代码、运行与测试、AI指导、求助教师 | 必做，先开发 |
| 学生·提交与复盘 | 成果快照、自我解释、AI协助记录、教师结果、迁移任务 | 必做 |
| 教师·任务设计 | 技能目标、任务材料、初始代码、测试、量规、教学策略和发布预览 | 必做 |
| 教师·课堂工作台 | 学生阶段、运行错误、主动求助、待复核项；查看证据后介入 | 必做，第二个核心页 |
| 教师·作品与评价 | 按量规复核、反馈、修改理由、成绩发布、学生申诉入口 | 必做 |
| 教师·成效与材料 | 班级任务总结、原始记录导出、匿名展示、效果对比 | 基础导出必做，统计增强后做 |

第一版以电脑浏览器完成编码；手机优先支持查看任务、接收反馈和求助。界面不展示API密钥、容器ID等运维细节。教师可看到任务资源不足、启动排队、失败和恢复等有助于安排课堂的状态。

## 4. 学生实训工作台

桌面布局：顶部为任务名、当前教学模式、保存/运行状态；左侧为任务书、技能目标和阶段步骤；中间为文件树与代码编辑，下面为输出/测试/作品预览；右侧为实训教练；底部提供求助教师与提交入口。

核心交互：

1. 打开任务，查看“要交什么、如何验收、可获得哪些帮助”。启动或恢复个人工作区，自动保存自己的修改。
2. 学生运行代码或测试后，AI读取与当前任务有关的错误、差异和已授权材料，给出可核对的诊断依据。截图可后续补充，首版以代码和日志为主。
3. 指导按“追问思路 → 定位与概念提示 → 局部示例”递进；是否提供示例由教师策略决定。不同学生可得到不同提示，学生随时可以请求教师帮助。
4. 普通指导模式默认不直接改代码。教师演示模式允许AI提出补丁，显示改动预览并由授权者确认。每次修改记录操作者与来源。
5. 每个阶段展示验收结果和教师定义的下一步条件。未通过时解释具体缺项，不以反复聊天次数充当掌握度。
6. 提交时保存代码版本、测试结果、学生解释和帮助记录，形成可复核的成果包。已经提交的版本不可被后续编辑悄悄替换。

状态必须覆盖：未启动、排队、准备中、就绪、运行中、已中止、资源到期、服务失败、已保存/保存失败。长任务支持取消，重试不产生重复提交；失败不展示虚假的测试成功或AI反馈。

## 5. 教师课堂工作台

默认展示当前任务的学生列表与需要关注的事项，而非大量综合评分图表。每条提醒给出事实及触发条件，例如“同一测试连续失败3次”“学生主动求助”，阈值可配置；网络故障、长时间未操作不直接判为能力不足。

点击学生后看到：当前阶段、最新提交或代码差异、测试结果、已给提示、学生解释、待确认事项。教师可补充提示、联系学生、调整该生指导级别、暂停某项AI动作，或向全班发布共性问题说明。介入原因与结果进入记录。

评价页将“自动测试结论、AI建议、教师确认”分栏呈现。AI给出的评分建议要附证据位置；教师可以修改并写明理由。高风险判断与正式成绩不由模型单独决定。

## 6. 教学控制模块与智能体职责

每轮流程：感知当前任务与运行证据 → 提出困难假设 → 选择符合教师策略的帮助方式 → 检查执行权限 → 执行允许的动作 → 观察结果 → 更新阶段建议。前端显示简短决策依据和执行记录，不展示模型内部思维链。

| 模式 | 可用能力 | 关键约束 |
|---|---|---|
| 引导练习 | 查看当前任务文件、运行诊断、分级提示、推荐教师审核的资料 | 只允许任务范围内动作；不自动完成学生全部作业 |
| 教师演示 | 生成局部方案、提出代码改动、演示运行 | 改动预览和授权确认；标记AI贡献 |
| 独立考核 | 任务与运行环境、教师规定的非答案帮助 | 服务端禁用解题/改码能力；保存考核策略版本；不承诺识别学生在系统外使用AI |

策略在后端执行，不只写进提示词或隐藏按钮。学生输入、上传文档和终端输出不能改变教师策略。模型密钥只在受控后端使用；学生容器只接收完成任务所需的受限资源。自动评分测试和参考答案放在学生不可修改的评价环境中。

现有OpenHands与DeepSeek接口作为基础组件；本项目的拟创新重点是可执行的教学策略、分层帮助和人机协同的过程评价。开源组件、改造位置和自研部分分别记录，参赛时不把SDK能力当成完全自研。

## 7. 一节课的设计示例

示例任务：“为一组企业FAQ资料实现检索、答案引用和无依据时的明确反馈”。课程时长由教师安排，不预设已开展课堂试用。

课前：教师选模板、修改材料、能力点和验收条件，试跑测试后发布。课中：学生先完成小型基础任务，进入分阶段实训；当检索结果为空时，AI依据实际日志追问数据加载和分词路径；学生解释并修改后重测；教师查看共性问题并做针对性讲解。课末：提交作品与解释。课后：在改变资料和边界条件的任务上检验独立迁移，结合教师反馈复盘。

任务自身的教学评价量规为：功能与边界测试40、调试解释25、方案与迁移20、工程规范与可复现性15。第四项依据 delivery_static_check、source_quality_review、delivery_review 以及 README、交付文件和可复现说明。它不是比赛评分标准。使用提示本身不直接扣分；独立能力由单独考核获得，不能靠字符数或AI修改比例推算。

## 8. 成效证据与数据口径

首轮选择一个真实班级和一项教学任务，记录实际人数、日期、课时、基础水平与任务版本。先定义成功指标，再开展试用，不能将草图示例数据写成参赛成效。

| 指标 | 采集与解释 |
|---|---|
| 独立技能表现 | 同一量规的前后测和变式任务；保存AI允许范围、教师复核与评分记录 |
| 任务达标情况 | 通过任务人数/实际参训人数，注明缺交、退出与缺失数据 |
| 调试学习 | 错误类型、修复后能否解释、后续类似错误是否复发；不能只看运行成功 |
| 教师指导负担 | 主动指导耗时、重复问题处理情况及教师简短记录；后台登录时长不能替代教学耗时 |
| 学生体验 | 帮助是否可理解、是否过早给答案、是否愿意再次使用等反馈 |

若条件允许用可比班级或任务交叉安排比较；前后对比需说明任务难度和学情差异，不凭一次演示断言效果提升。证据以脱敏ID保存，教师和学生只访问授权范围，导出支持匿名版本。

## 9. 分阶段实现与验收

阶段A：两个核心页面的交互原型，使用明确标注的示例数据，确认任务布局和师生流程。

阶段B：一个真实任务闭环：登录、教师发布、学生独立工作区、编辑与测试、一级/二级指导、求助与介入、提交快照、教师复核。接通后端与模型，并至少覆盖一个正常案例、一个错误诊断案例和一个服务失败恢复案例。

阶段C：课堂试用、基础数据导出、独立迁移测评和匿名演示入口。单机环境先限制实训并发并做压测，不把“两容器检查通过”表述为已支持一个班同时运行；据实测决定排队或服务器部署。

阶段D：扩充任务模板、可视化成效分析、截图诊断和更完整的编辑器体验。语音、数字人、复杂知识图谱与跨校管理不作为首版前置目标。

首版验收以一位教师从发布到复核、两位学生各自完成任务为最小真实链路，不能用页面按钮可点代替业务接通。评审前提供可访问的应用入口和测试账号；目前本机Docker可用不等于已经公网部署。

## 10. 演示与材料

演示入口提供独立的示例课程、学生与教师测试身份，数据与正式课堂分开，可重置。页面和录屏使用匿名标识；文件名、日志、导出和截图一并检查。展示一个“出现错误—分层指导—学生解释和修复—教师查看—独立迁移验证”的案例，再呈现实际应用证据。

示例记录、系统运行日志、真实教学效果分别标注来源。材料支持查看任务版本、代码提交记录、自研模块和依赖清单。证据导出只是整理工具，最终原创性说明、学校审核和盖章仍按赛事要求办理。
